# 第一次使用的验收

验收必须在新实例中完成，不继承作者的运行目录、私人账本、角色绑定、手机或消息账户。测试材料放隔离账本；正式交付账本保持用户自己的内容。

| 环节 | 可接受证据 | 不能替代的材料 |
| --- | --- | --- |
| 安装 | 干净目录解包、清单通过、依赖安装、服务存活、Web 返回 | 原机器已有依赖或旧服务正在运行 |
| 自带 Agent | 用户选定 CLI 实际执行并返回，本实例默认职责指向它 | 只检测到了二进制路径、登记成功或模拟在线 |
| 无额外账户 | 未要求模型 key，未连接 iMessage 仍能进行核心流程 | 关闭报错但后台职责仍指向未配置的模型服务 |
| 微信交代 | 用户本人扫码后在微信输入自然任务，服务真实接收并在同一对话回复 | 构造的 Webhook、Web 输入或 fixture；它们只能验证适配链路 |
| 手账入账 | 用户确认后得到正式事项 ID、日期等已知事实与版本 | 模型口头说“已记下” |
| 自动组件 | 自带 Agent 返回通过校验的设计提案，布局来源、事项绑定和 Web 实际组件一致 | 只有基础投影、模型失败后保留旧布局 |
| 任务中断恢复 | 停止本实例／退出执行器后，重启仍读到同一事项并继续，没有重复建账或重复外部动作 | 新建另一件同名事项重新开始 |
| Web 改动继续 | 改期、记下候选或勾步骤后，微信继续时读取最新账本事实 | 依赖旧对话文本猜测事项进度 |

推荐最小场景：用户说「帮我准备周日的生日」。也可从 [生活与工作四个场景](starter-scenarios.md) 选择用户当前需要的一件，沿用同一验收标准，不把资源齐全记为全部场景通过。相对日期由当次可信日期与时区解析；缺少寿星、预算或人数时只追问真正影响下一步的问题。确认计划后先呈现准备清单；只有存在候选材料才增加比较，有预算材料才加预算。不要为了展示 20 种组件一次生成 20 张空卡。

在已经确认计划后中断并重启，用户接着说「改到下周日，先做已经确定的准备」。核对原事项身份保持、日期更新、原步骤和草稿保留。没有外部订座或发送证据时，状态仍为准备／待确认。

最后报告实际通过项和唯一未完成项。如果只差用户扫码，给出当前可打开入口和扫码步骤；不要宣称真实微信闭环已经通过。默认不为了验收增加第三方联系人、发测试通知或请求所有可选权限。

## 自动整理属于独立验收项

安装器的 `connect --desktop-pet` 配置 Mac 数据连接桥、后台观察服务、独立桌宠及回复通道。第三方 OAuth 应用由发布方预配置，用户本人在官方页面授权。仅在页面勾选「自动整理与兴趣」不能证明有后台生产者。用 `automation-status` 核对所选来源、真实手账条目和当前通道回执，再观察桌宠实际显示。缺项明确列出，不借用作者实例的配置或运行结果。

新用户默认留空兴趣话题和账本，不携带作者的阅读表达偏好或反馈。用户的语气反馈与话题反馈分开记录。验收至少包含一条真实来源自动入账，以及用户反馈后另一轮实际产出携带对应偏好证据；隔离测试和单纯保存反馈不能替代。X 还需要发布方预先配置应用和用户本人授权，不要求普通用户填写 Client ID 或 Secret。

验收记录应包含发布 ZIP 和内嵌框架哈希、全新目录、模型真实返回、各来源授权/读取状态、自动扫描时间与条目 ID、原始来源链接、投递时间与 channel/delivery ID。不得直接调用 offer、回填业务表或发送写死的测试文案来冒充自动产出。未到通知时间或处于免打扰时继续观察；要临时改通知时机先取得用户同意，收到后恢复。

停止并重新启动新实例，确认只恢复自己的后台进程、账本不丢、旧投递不重发。完成桌面验证后关闭 Computer Use 和本次临时浏览器，保留少量关键证据。
