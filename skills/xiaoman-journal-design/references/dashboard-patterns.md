# 看板组合 · 随任务阶段改变

这组模式回答「为何放在一起」，不是每位用户必须出现的预制看板。只使用输入真实事项、`availableKinds`、当前阶段和已知材料；下表不存在的材料不能自动补齐。

## 先决定主线

1. 用户现在要做什么：补条件、排时间、做准备、选方案、等待、恢复还是留下经历？
2. 一张主组件能否承接下一步？辅助组件是否提供另一种必要材料？
3. 现有布局仍适合吗？若仅更新时间、文字或某一步状态，继续原组件。
4. 有无用户固定／隐藏／排序、正在编辑的内容或暂停自动整理？遵守这些决定；不要以“更美观”为由推翻。

一个事项常用 1–3 张；全局最多 12 张、最多一个主焦点。不要把 20 个可用种类理解成 20 个默认必选模块。

## 组合模式

| 模式 | 主组件 → 辅助 | 使用理由与摆放 |
| --- | --- | --- |
| 准备一场生日 | `prep` → 有预算材料才加 `budget`；确有待选材料才加 `decision` | 步骤承接准备；预算回答够不够；比较回答选哪个。比较独占完整行，不与采购挤成两个窄列 |
| 决定去哪里 | `decision` → 已知冲突时加 `time-grid`，确定后才用 `agenda` | 候选约束先于评分；选方案与选时间可并存，但不能凭偏好宣称实单可约 |
| 办一次手续／搬家 | `documents` 或 `deadline` → `prep`；有明确阻塞才加 `recovery` | 缺哪个文件、什么时候到期、接下来做什么是三种问题。材料列表不是官方已核验清单 |
| 周末出行 | `itinerary` → 预算有限且有材料时加 `budget`；需要准备才加 `prep` | 站间移动不能埋进待办；缺失直连时长留待核实；固定返程约束不可被排版省略 |
| 过好今天晚上 | `meal` 或 `agenda` → `shopping` 或已有 `habit` | 当前做饭步骤与份量是主线；买菜是此前阶段，不重复显示已经完成采购的大卡；习惯不随便与其他事项合并 |
| 等一个结果 | `waiting` 或 `delivery` → 有真实截止才加 `deadline` | 等人回复与履约链二选一；只是等待时不制造受阻；有缺口且原计划无法继续才换 `recovery` |
| 交给别人做 | `handoff` → 对方确实收到请求后才加 `waiting` | 用户的分工与对方的确认分开。出站发送由管家另行执行，设计不发送 |
| 留下一个灵感 | `collection` 单张 | 允许多项共存，不强行加入比较、预算和购买计划 |
| 收好一次经历 | `reflection` → 用户已有想留的文字时加 `memory` | 先给感受输入的空间，保留原话；未写评价不自动生成评分或偏好 |

## 四种入门场景的选型差异

管家提供生活两个、工作两个入口。设计输入只包含已正式保存的材料；下面是判断结构的参考，不授权设计职责读取来源、创建任务或执行动作。

| 场景与当前问题 | 主组件 → 可选辅助 | 随阶段调整与不应出现的内容 |
| --- | --- | --- |
| 生日筹备：现在先准备什么 | `prep` → `budget` 或 `decision` | 有真实候选才突出通栏比较；活动确实结束后才转评价。无候选、预算和结束证据时只保留准备 |
| 晚餐与采购：还缺什么／开始怎么做 | 采购阶段 `shopping`；烹饪阶段 `meal` | 物品数量与烹饪步骤分开；已买清单不重复占主位。调份量不等于采购量已同步，设计不能代替业务服务更新事实 |
| 邮件日程整理：今天何时处理什么 | 已定时间用 `agenda`；本人行动用 `prep`；确有截止时考虑 `deadline` | 按当前主要问题选一个焦点。摘要留在对话或事项摘要，不另造邮件收件箱组件；未读邮件不能变成已确认待办，过期事项不拿来凑推荐 |
| 项目会前准备：凭什么判断／还需定什么 | 材料阶段 `documents` → `prep`；决定阶段 `decision` → `documents` | 文件详情放来源与缺项；比较占完整行。无真实选项不做比较，无负责人不加交接，无会议结果不生成回忆 |

生活场景分别重在步骤和物品，工作场景分别重在时间与证据。共享一个组件并不要求同一种看板：随主动作和材料改变组合。查询覆盖不足、待确认日期和不可读文件在原结构中保留真实缺项；不因想表达“不完整”就额外堆一张 `recovery`，只有明确阻塞和可行恢复分支才需要它。

## 生日场景贯穿

**一句交代。** 「帮我准备周日的生日。」若尚未确认计划，不创建正式事实或凭空给寿星命名；由管家确认真正影响行动的条件。相对日期按当次可信日期与时区解析，不从本参考中取日期。

**计划已确认。** 步骤已入账，选 `prep` 为主。若账本只有步骤与日期，不强行加预算、采购、邀约、照片或候选。日期可以在事项摘要呈现，不必再造一张重复议程。

**有候选待选。** 若管家已经获得两份可比较材料，`decision` 可成为主，`prep` 为辅助。比较采用共同字段；“库存未知”保持可见，便宜或距离近不能代替可约证明。

**改期。** 更新正式日期后，原事项和组件 ID 继续使用。已知报价有效期、可选时段或确认内容受影响时，由业务服务重新核实或作废选择；设计不得沿用旧确认制造已完成状态。

**选择之后。** 选择已记下，比较保留回看入口。只有账本明确有对外请求时才加入 `waiting`；没有请求材料不为凑阶段生成空等待。

**中断再回来。** 用账本版本恢复原步骤、日期、候选和用户布局偏好。组件刷新原位置，草稿继续存在。设计失败则保留账本与上一个有效布局，不从对话猜测、重复建账或清空界面。

**生日结束。** 有结束事实后可用 `reflection`；用户填写后再以 `memory` 回看原话。只完成某个步骤、选候选或确认计划，不能把整场生日提前归档。

## 组合的视觉约束

主内容在前，辅助在后，来源与管理按需展开。通栏比较、文件双面目录和路线不强塞半宽。短预算和短准备可以在各自宽度足够时并排，手机按同一阅读顺序堆叠。不要为填空重复摘要、自动生成不必要的卡，或用照片当作所有类型共同的视觉骨架。


## 连续工作页与试算

同一事项的准备、候选、预算、采购和食谱共享标题、来源、进度和收尾。每页突出一个与真实下一步匹配的主区；其余用紧凑摘要，展开后继续原组件操作。用户固定、隐藏和排序优先；全局交错的事项不得强制重新聚拢。

调整已记录的人数/总预算时，先展示只读影响表，再采用。食谱份量按基础人数推导；采购仅在同事项内名称与单位唯一、原量相符时联动。已买、在家、已完成状态保持。价格不推断，不按人数缩放预算明细。未知库存、用量或报价显示待核实。

Web 草稿按事项保存，刷新后恢复；采用前重新核对 revision 和 itemVersion，过期试算不能采用。保存丢失回执时使用同一请求身份核对，不能重复修改。微信通过相同 preview/apply-preview 工具访问正式账本。

渐进呈现以完整、已校验的正式材料为单位：基础结构先可用，设计提案完成后再局部整理。保留组件 ID、焦点、阅读位置和草稿；不把半段 JSON 显示成有效结果，不每次点击调用模型。
