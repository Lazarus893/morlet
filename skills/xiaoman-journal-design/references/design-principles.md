# 通用设计理解 · 安静的管家

## 从生活意图到信息结构

打开手账，用户应先知道「进展到哪、现在可以决定什么」。先判断主要动作，再看可用材料，最后选择结构。生日只是题材：找日子需要时间网格，采购需要数量清单，选餐厅需要同字段比较，受阻需要恢复路径，结束后才需要评价。

一张组件成立，至少要有明确问题、独立材料结构和可理解的动作或阅读目标。改标题、颜色、照片或圆角不构成新类型。遮住标题后，用户仍应能从布局辨认它是在比较、准备、等回音还是写感受。

优先展示用户可以推进的下一步；不是按后台模块平均分配面积。一次事项通常一张主组件加零至两张辅助。辅助必须回答不同问题：准备的步骤、候选的限制、预算的余量各有价值；三次重复事项简介没有价值。

## 层级与密度

稳定阅读顺序为「事项身份与阶段 → 当前决定／行动 → 辅助材料 → 来源与管理」。事项摘要紧凑，不套巨大封面卡；步骤用行，比较用共同字段，回忆用阅读页，文件用目录与详情。每层边框必须有分组作用，避免卡里再嵌一组等价卡。

页面最多一个主焦点，主动作有明确对象。管理、来源和整理理由按需展开，不让调试字段或模型长篇推理占据生活内容。模型选型的 `reason` 是可解释记录，不是必须向用户展示的大段产品文案。

核心事实和限制在可见区：日期、人数、金额、具体分店、哪条条件未知。长备注可以展开，关键不满足条件不能藏在省略号里。状态写「已记下」「已选择」「待核实」「已暂停」等具体含义，不用泛化「完成」包办所有结果。

## 宽度与排布

- 内容最大宽 1120px；外侧间距窄屏 16px、中屏 24px、宽屏 40px。正文宽度服务内容，不必填满最大宽。
- 候选比较占完整行。双候选每列至少 340px，列间 20px，**组件内部**可用宽度至少 700px 才并排；如果外层有边框和 24px 内边距，外框需要约 750px。不能仅因浏览器窗口大于 700px 就强制双列。
- 两候选的字段顺序和单位一致，关键条件对齐；1 个候选用紧凑单行／单列并写「目前一个」；3–5 个用共同字段比较列表，不留一张孤立半卡。
- 两块辅助只有同级、相关、各自可读时才并排。单独剩余组件占完整行；不造内容填空，不用固定双列把核心比较压窄。
- 外层有序行，默认不用瀑布流。窄屏只变宽度，不重排用户事项、材料或键盘顺序。

## 排版与颜色

| 角色 | 基准 |
| --- | --- |
| 字体 | Avenir Next / PingFang SC / Microsoft YaHei / sans-serif；无需联网字体 |
| 页面标题 | 30–32px，行高约 1.35，字重 500–600 |
| 事项标题 | 24–28px，行高 1.4 |
| 组件标题 | 20–22px，行高 1.45 |
| 正文与条件 | 16px，行高 1.6；手机不缩小 |
| 辅助信息 | 14px；数字用 tabular-nums；重要数值维持正文字号 |
| 间距 | 4 / 8 / 12 / 16 / 24 / 32 / 40 / 48px |
| 背景／正文／主动作 | `#F7F8F5` / `#242C27` / `#315C47` |
| 次级正文／边界 | `#59665E` / `#DCE3DA`；输入边界 `#6D8071` |
| 待核实／失败 | `#865537` 配 `#FAF3EB` / `#9A3C2F`；同时有文字 |

正文与背景对比至少 4.5:1，焦点与控件识别至少 3:1。装饰分隔线不能当作唯一控件边界；不是所有状态都用绿色。普通组件 12px 圆角，控件 8px；阴影主要表达浮层，不让所有内容浮起来。

## 用户偏好与稳定性

`pinned`、`hidden` 和 `order` 是用户已经作出的展示决定。保留稳定的 `<itemId>:<kind>` 身份，由服务在提案外统一落实偏好；不能生成另一 ID 让隐藏组件重新出现。编辑中的内容、草稿和焦点不能被自动整理带走；必要时由展示端提示「看板有更新」后再应用。

普通文字、价格或时间刷新更新原组件。只有任务阶段、用户意图或可用材料发生变化才考虑换结构。选择后保留其他候选的回看入口；任务结束后先记录感受，再收进回忆，不用动画把用户还在看的内容突然移走。

## 事实边界

正式账本是唯一事实源。设计不得创造人名、数量、金额、评价、库存、交通时间、照片、来源或执行回执。未知数字用 null／待补，不能用零充数；预览截断不意味着原材料不存在。例图、配色和静态看板只是设计参考，不能当成真实商品、用户经历或已授权材料。

尤其分清：安排不等于预订，确认计划不等于执行，用户选商家不等于商家接受，草稿不等于消息发送，文件标记提供不等于已读取／机构核验，提醒计划不等于通知送达，分工记录不等于对方接手。

能力由当次 `capabilities` 确定；参考资源不能扩充权限。作为设计职责运行时只返回布局，业务修改通过管家的正式账本工具、用户意图、版本与服务端校验完成。
