# Morlet 手账

> 当前入口：在「聊天 → Mori」交代任务，需要保存的结果进入手账。本文带日期的早期实现与独立账本指令保留为历史说明；当前界面以本文书签手账与首次使用部分为准，执行规则见技能的 runtime-workflows。


Morlet 保留安静、克制的手账方向。Mori 负责收件与分派，事务 Bot 按职责协作，Web 手账用于查阅产物、核对选择和继续处理。本人验证后的消息路线共享对应聊天，未验证联系人保持隔离。

## 开始使用

运行 `./scripts/pa.sh web`，打开本机 `http://127.0.0.1:3083/`。没有微信账号也可以在 Web 聊天里交代一件事，保存有用的结果后回手账查看。

- 安排、购买、经历、愿望：标题、可选日期、材料/评价、准备步骤、候选及材料链接。
- 从事务、巡查、资料目录或页边书签打开一件事；同源时序资料默认只展示最新一期，历史仍可回看。
- 「产物」查看情况说明与 Widget，「对话」继续补充。搜索和归档显示选项用于找回已有记录。
- 悬停或聚焦 Widget 后可拖动排序，也可用键盘操作，顺序自动保存；显示选项保留已有隐藏组件的恢复入口。
- 步骤勾选不自动结束整件事；候选选择只记下决定，不表示已经付款。
- 结束后可以补充评价/备注；改日期或准备材料需要重新打开。取消保留来源，删除会移除记录及展示。

### 早期独立账本指令

以下为原独立账本入口，保留作历史接入说明；当前普通聊天不需要使用这些命令。微信必须已登录、私聊且发送者已在白名单：

```text
手账 新增 给妈妈准备生日
/journal add 给妈妈准备生日
/journal
/journal done <事项编号>
/journal cancel <事项编号>
/journal undo <事项编号>
```

也支持“手账 完成 / 取消 / 撤销 编号”。编号从 `/journal` 列表查看。在网页「正在查看」切换到对应微信用户账本继续补充，原微信来源保留。本机手账和各账户/用户分别存储，当前不做隐式合并。普通聊天不会全部进入手账。

## 默认设计 Agent

正式角色随源码放在 `agents/life-journal-designer/AGENT.md`，由 Chief 管理，无需依赖开发者机器上的设计技能路径。该角色继承已选品牌、组件层级与动效约束。

新增、结束、取消、撤销、选定候选，或实际改变事项类别/步骤/候选时，后台尝试整理。普通日期、备注、勾选更新直接刷新原组件；固定和顺序保持稳定。可暂停自动整理，也可手动请求重新整理。

设计 Agent 读取最多 30 个优先事项及必要的展示偏好，输出最多 12 个 Widget 的 JSON 提案。它没有执行工具；不会输出可执行 HTML/JS，不修改业务事实，也不发送微信。布局可含最多一个主焦点，绑定的事项与组件类型必须通过校验。固定、隐藏和排序规则最终由可信展示服务处理。

DSH 使用运行中的本地 PA 模型上下文；未连接该服务时显示基础排版。Codex/WorkBuddy 使用已保存的核心、模型与解析后的 CLI 路径，在独立分析目录以 passive 会话运行。检查到 CLI 并不证明已登录或额度可用；失败会保留现有布局。普通打开页面不会调用模型；已存在队列在获得授权后可以恢复。

DSH手账设计调用单独使用8192-token输出预算，普通观察分析默认仍为1600。最终分析文本限制为16KiB，截断或缺少正常结束信号不会发布部分提案。`xiaoman_journal get`返回真实`design`状态和`layoutSource`；保存成功、存在基础组件或已有Agent版式，均不能单独表示这次AI整理成功。只有当前账本revision对应的设计状态为`ready`时，才可声称本轮设计完成。

## 数据和任务一致性

正式记录保存在 `.runtime/life-journal.sqlite`，不进入 Git 或源码包。短 SQLite 事务与版本校验允许微信/Web 跨进程共用。每次修改携带账本版本，可附事项版本；冲突不会覆盖另一端修改，编辑器保留草稿并要求重新校对。

模型任务另有持久化 token、基准版本和布局版本。排队/运行/成功/失败分别显示；迟到结果不能覆盖改期、隐藏、暂停或删除后的记录。两把内核锁限制全局最多两个设计调用，单 scope 锁避免重复认领；进程退出由内核释放锁，恢复不伪称未确定的任务已完成。恢复与执行均受当前账户和用户授权检查。

事实来源在录入时保存，后续编辑保留原文与当前版本。公开 HTTP 不允许提交内部模型结果，也不接受客户端伪造微信来源。重复微信指令按稳定消息编号去重，重启或删除后也不重建旧记录。

## 动效

使用 CSS 与 Web Animations API，复用组件身份和焦点：新组件渐入、数据更新局部反馈、真实提醒状态变化一次强调、重排 FLIP、展开收起过渡。普通轮询不重新播放整页，初始历史提醒不补播。

用户可选择跟随系统、减少动态效果或关闭动效。减少动态效果保留短淡入与文字状态；关闭时直接呈现终态。动效在后台标签页停止，不参与业务提交或实际发信。

## 目前的边界

没有实现自动获取商家候选、订单/支付、附件照片上传、自动日历订阅、远程手机访问或全领域蜂群。手账日期尚未直接创建主动提醒任务；提醒展示读取现有跟进台账，实际微信发送继续受主动开关、上下文、静默与额度规则控制。电脑休眠及跨日送达仍需真实运行验收。

第一轮验证使用临时账本、真实 HTTP/SQLite/Designer/DOM/WAAPI，以及离线模型/通道替身。2026-10-12 真实 DSH 已重载，真实模型生成与本机生日业务流程也已验收；未代用户发送微信、调用真机或购买。验收证据见 `docs/verification-life-journal.md`。

## 首版实例的生日试用 · 2026-10-12

打开 `http://127.0.0.1:3084/`。微信已连接，若「已允许」仍为零，从自己的微信先发一句话，到 Web「连接」核对待配对用户并允许本人，再发送正式指令；未允许时的消息不会补写入手账。

1. 微信发送 `手账 新增 给妈妈准备生日`，等待保存回执。
2. Web「生活手账」的「正在查看」选择对应微信用户，看到新事项及自动整理的焦点组件。本机手账是另一份账本。
3. 点「查看与校对」，填写实际日期、人数/预算备注、准备步骤（每行一项）、已有候选（每行 `名称 | 说明 | 网页链接`，链接可不填），保存后自动生成适合这些材料的组件。
4. 再次校对修改日期，原组件更新；在候选比较组件选定一个候选，并逐项勾选准备步骤。选择仅记录决定。
5. 点「确认结束」，到「留下来的」打开该事项补评价，保留来源及准备记录。

首版微信新增指令只记录标题；日期、步骤及候选需在 Web 补充，不自动查商家或创建微信提醒。若模型整理失败，可点击「重新整理看板」；已保存事实与基础组件仍可使用。2026-10-14 新增的 Hub 工具路径见下文。

## 结构化生活组件 · 2026-10-14

本轮把实验室的20种任务结构接入正式账本契约。控件库负责按钮、输入和选择等基础交互；下面20种是分别组织生活事实与动作的业务结构，不能用20种基础控件代替。数据来自已保存的事项与材料，展示不读取实验室样例。

| 类型 | 组织的事实 | 可保存的主要动作 |
| --- | --- | --- |
| `agenda` 今日议程 | 事项日期、时长、地点 | 记下安排时间 |
| `time-grid` 可选时间 | 候选时段、所需时长、缓冲与已有约束 | 记下不冲突的时间偏好 |
| `prep` 分阶段准备 | 准备步骤与阶段归属 | 记下某一步完成 |
| `decision` 条件比较 | 候选、费用、尺寸与比较字段 | 记下满足已录硬条件的候选 |
| `budget` 预算拆分 | 总额、费用项目、未知报价与预留 | 修改预留金额 |
| `shopping` 分组采购 | 物品、数量、单位、家中已有与已买状态 | 修改数量、记下已买 |
| `itinerary` 路线站点 | 地点、可选站点与已核实路段 | 记下省略哪些可选站点 |
| `waiting` 等一个回音 | 联系对象、所问事项与回音状态 | 保存催询草稿 |
| `delivery` 履约进度 | 已录阶段与有时间、来源说明的回执 | 追加本人或执行 Agent 已核对的回执 |
| `deadline` 期限与下一步 | 截止时间与下一步安排 | 记下截止前的下一步时间 |
| `reminder` 事件提醒 | 事项时间、提前量与计划记录时间 | 保存提醒计划 |
| `habit` 习惯周历 | 用户时区、目标与打卡日期 | 记录或撤回某天打卡 |
| `meal` 做饭步骤 | 基础人数、已知食材用量与烹饪步骤 | 调整人数、记下步骤完成 |
| `collection` 灵感收藏 | 用户提供的标题、原话和链接 | 增加收藏材料 |
| `documents` 材料夹 | 材料名称、备注与是否已提供 | 记下材料已提供或缺失 |
| `approval` 执行前确认 | 计划内容、金额、时间与条件 | 确认或撤回这份计划 |
| `recovery` 受阻后备选 | 阻塞、已知与缺失材料、下一步方向 | 记下选定的下一步 |
| `reflection` 结束评价 | 评分与体验原话 | 保存评价 |
| `memory` 回忆手账 | 想留下的原话、发生时间与题注 | 保存记忆 |
| `handoff` 家人分工 | 参与者、任务与交接条件 | 修改一位负责人 |

每个事项保存 `taskType`（`auto` 或一个正式类型）与 `taskData`（按类型分开的材料）。一种事项可支持多个结构，比如生日同时具有准备、预算和等待回音。`auto`模式允许AI从当前阶段适合的结构中选空态：标题说生日可选准备，说预算可选金额结构，缺失事实仍等待补充。基础排版按已有材料呈现，只有标题时先显示一张议程，不铺满18张空卡。明确指定类型时，只能选择该意图和已有材料支持的结构；尚未发生的安排不能被自动当成回忆或结束评价。只有标题的交代不会自动获得商家、预算、订单或路线资料，未知报价、数量与路段时间保留 `null`，不显示成已核实的零。

设计 Agent 只选择该事项的 `availableKinds`，不能修改材料。输入最多30个事项、输出最多12个组件和一个主焦点；材料预览每组最多8条、字符串最多400字，整次输入最多128KiB，仅用于选型，组件读取完整账本。固定、隐藏和排序仍由可信层决定，模型省略固定组件或重新提议隐藏组件不会绕过偏好。未单独记录时区的习惯采用实例时区，用户已记录的时区保持不变。

### 从日常交代进入账本

已获得本轮工具的 Hub 执行 Agent 可通过 `xiaoman_journal` 查询结构和现有记录，再写入用户明确交代的事项与材料；Web 继续修改同一条正式记录。工具从获准的执行任务取得真实入口来源，使用本机 owner 的共同生活账本，不接受 Agent 自报的 scope 或来源。一次调用的编号和载荷绑定，成功回执可重用。`apply-preview` 在账本与回执同一事务提交，因此进程在账本提交后、Hub 回执完成前中断时，可以核对同一请求而不重复修改。其他跨库写入没有这种回执，结果不确定时仍须先读取现有记录，不能直接重放。

这条路径需要 Agent 实际调用工具，不会把全部聊天、全部 Hub 任务或一段普通回复自动归档。`/journal` 与“手账 新增”等旧微信确定性命令仍保留按账号/发送者分开的历史账本，不隐式并入 owner 账本。原有 Codex 会话不能通过 resume 追加 dynamic tools；新工具用于创建时已登记它的新会话。旧会话保留原上下文，不能把部署源码视为已向旧会话注入工具。后台设计角色继续使用已绑定、实际可用的宿主能力，不因聊天连接了另一个执行端而改写职责。

Agent修改已有事项前先调用`get`，复用返回的`writeTemplate`中的revision、itemId和itemVersion，并把全部变更放入`values`，包括领域动作的kind/action/data。遗漏版本或把变更写到顶层时，工具返回`saved:false`及结构化纠正说明，账本不改变；宿主不会自动补版本或接受旧的扁平写法。正确包装仍受CAS保护，拿过时模板提交会被拒绝。只有`saved:true`及相符的正式事项回执才能作为已保存的依据，授权、来源伪造和执行租约检查保持严格。

### 记录动作与外部执行

时段偏好不表示预约，候选选择不表示下单，采购勾选不执行购买，催询草稿不发信，材料状态不读取附件。事件提醒组件目前保存计划、计算计划时间，不会凭该动作新建通知或保证送达。执行前确认只确认账本计划，不替代 Hub 的真实执行审批；日期、金额或其他相关事实变化后，原确认失效。履约进度只展示已录证据，不能依据组件阶段推断第三方订单已成功。

正式写入继续检查账本 revision；`widget` 领域动作还必须携带事项 `itemVersion`。字段与跨引用先校验后提交，失败不改变已保存的事实；结束后仅开放评价、记忆及原有备注补充。取消事项保留来源，不允许继续领域写入。

旧SQLite记录与旧7种组件身份继续可读。旧 `focus/checklist/comparison/timeline/wish` 分别呈现为议程、准备、比较、议程、收藏结构，`waiting/memory` 同名；原固定、隐藏、排序和隐藏组件缓存保留原ID。新模型提案只接受20种正式类型。代码、HTTP、实际界面与内网部署的验收范围分别记录在[本轮验证](verification-first-task.md)，不由组件目录推断全部外部能力已通过。


## 连续任务工作页 · 2026-10-18

同一事项的组件共享标题与来源。主区由已保存事实确定，候选、采购和做饭不会同时争抢主位。当前每篇拥有自己的组件，排序只调整本篇对应位置，保留其他篇与隐藏组件的已存顺序；不会因排序把一篇拆成多个片段。设计 Agent 可提供受限的 section（next/plan/reference）与 presentation（expanded/compact），不能返回自由代码或改写业务阶段。

Web 可试算已有食谱人数和预算总额：POST /api/journal/preview 只读展示影响，POST /api/journal/apply-preview 用 revision、itemVersion、previewHash 与持久 requestId 一次采用。首次采用在 SQLite 事务中重新计算并比较预览；重复请求不会多写，改载荷复用同一请求 ID 会冲突。其他入口改动后，旧预览不能覆盖新记录。

食谱份量按 baseServings 推算，待买条目只在名称/单位唯一且原量对应时联动。已买、家中已有、完成进度和未知对应项保留；不推算价格，不按人数缩放费用。总预算不能低于已记录明细加预留；未报价项目仍提示未知。预览草稿刷新保留，但采用前须重新核对版本。

xiaoman_journal 的 preview/apply-preview 复用同一确定性域逻辑，受配对、任务租约与首次任务确认保护。`applyReceipt` 标识原提交的版本；核对时返回的 item/revision 是当前快照，可能包含之后的修改，不能把新版本归功于原请求。普通按钮不会反复调用模型；正式基础材料先可用，设计完成后按稳定组件 ID 局部整理。保存、设计完成和外部执行仍是不同回执。

邮件与日程的最终回复会附本轮来源桥实际回执生成的读取范围：每个邮件查询分别计数，区分完整正文、部分正文与未完整读取；日历保留 primary、原始起止及时区偏移、分页是否列全。失败和在途读取单列，不能按零条结果解释。这只证明读取范围，正文结论仍需核对来源；覆盖说明与最终消息一同持久保存，重复完成事件不会再次投递。

## 书签手账 · 当前界面

用户确认的 Image Gen 方向已落到正式前端源码。桌面是左侧目录、右侧当前任务的双页手账，页边书签最多显示四篇；完整任务索引可搜索和滚动。点击书签或上一篇／下一篇会打开任务首部并聚焦标题。手机采用单页与可展开的“书签目录”。

目录按事务、巡查、资料分组。篇目、产物／对话选择、搜索与滚动位置会在返回时恢复；用户刚作出的新选择优先于迟到的恢复。切换和筛选不写账本；后台更新不应把正在读的任务换掉。完成或删除当前任务后显示下一条可用记录或空页。

阅读默认不常驻手动灵感、材料和负责人编辑表单；需要改要求时回到对话。具体选择、授权、归档及失败恢复仍在对应位置。当前情况说明完整呈现，历史结果与文件收起；原交代和 Bot 回报分别定位精确消息。搜索无结果时可以清除筛选，已有材料不会因此删除。

框架仍使用现有 OpenUI React 组件、主题和正式动作；手账外观集中在 `journal-notebook.css`，无新增依赖或运行时生成图。设计审查覆盖视觉、可访问性和状态；隔离 HTTP/SQLite 与浏览器验收入口见 [Web UI](webui.md)。实例设计记录和测试截图留在开发环境，不随框架分发。

### 从真实材料开始的引导

空手账的「找 Mori」只读查询本机账本近 14 天有正文分析和来源摘录的邮件/GitHub 材料，将其中一条带入 Mori 固定私聊的可编辑草稿。没有材料时先请用户提供资料，不自动生成会议或其他样例。

打开入口不创建引导事项或执行任务；用户发送后才重新核对来源并处理，产生有用结果时再入账。已有未发送草稿保留，需要明确选择追加外带内容。读取范围和未确认事实保留，持续跟进与外部动作仍需对应授权。

旧空白引导不再占据普通手账目录；已有成果与原历史仍保留，旧入口能转到对应成果。新的情况说明回答当前事实、结论、变化与必要决定，不用保存回执代替内容，也不改写历史正文来制造新结论。详见[首次使用](onboarding.md)。
